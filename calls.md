## P2P-звонки (аудио/видео)

Звонки реализованы через **WebRTC**: сам голос/видео идёт напрямую между
устройствами (peer-to-peer), сервер не проксирует медиапоток — он только:
1) заводит и ведёт состояние звонка (кто кому звонит, когда ответили/завершили),
2) сводит собеседников (сигналинг: обмен SDP/ICE через уже существующий WebSocket),
3) будит оффлайн-собеседника пушем.

Пока поддерживаются только звонки 1-на-1 в личных чатах (групповые P2P-звонки
плохо масштабируются mesh-топологией без отдельного SFU-сервера — это возможное
дальнейшее развитие).

### REST-эндпоинты

| Метод | Путь | Описание |
|---|---|---|
| GET | `/calls/ice-servers` | Конфигурация STUN/TURN для `RTCPeerConnection` на клиенте |
| POST | `/calls/{chat_id}/start` | Начать звонок в личном чате (`call_type`: audio/video) |
| POST | `/calls/{call_id}/answer` | Принять звонок (только вызываемый) |
| POST | `/calls/{call_id}/reject` | Отклонить звонок |
| POST | `/calls/{call_id}/end` | Завершить звонок (любая сторона) |
| GET | `/calls` | История звонков текущего пользователя |

### Сценарий звонка

1. Звонящий: `GET /calls/ice-servers` → настраивает `RTCPeerConnection`
2. Звонящий: `POST /calls/{chat_id}/start` → сервер создаёт запись звонка
   (статус `ringing`), шлёт вызываемому WS-событие `incoming_call`; если тот
   офлайн — дополнительно шлёт push (см. ниже)
3. Звонящий создаёт SDP offer и шлёт его через WS: `webrtc_signal` с
   `signal_type: "offer"` — сервер слепо пересылает payload второму участнику
4. Вызываемый: `POST /calls/{call_id}/answer` → сервер шлёт звонящему WS-событие
   `call_answered`; вызываемый создаёт SDP answer и шлёт его так же через
   `webrtc_signal` (`signal_type: "answer"`)
5. Оба клиента обмениваются ICE-кандидатами через `webrtc_signal`
   (`signal_type: "ice_candidate"`) до установления прямого P2P-соединения
6. Любая сторона: `POST /calls/{call_id}/end` → второй участник получает
   `call_ended`

Если вызываемый не отвечает `CALL_RING_TIMEOUT_SECONDS` секунд (по умолчанию 45),
сервер сам переводит звонок в статус `missed` и уведомляет обе стороны событием
`call_missed`. Если участник разрывает WebSocket-соединение прямо во время
звонка (краш, потеря сети, приложение убито) — сервер тоже сам закрывает звонок
и уведомляет второго участника событием `call_ended` с `reason: "peer_disconnected"`,
чтобы тот не "завис" в разговоре с отвалившимся собеседником.

### Push о входящем звонке

Если вызываемый не подключён к WebSocket, сервер шлёт **data-only** push
(без `notification`-блока) с `data.type = "incoming_call"`, коротким TTL
(~25 сек) и высоким приоритетом — клиент сам решает, как показать входящий
звонок (полноэкранный UI, рингтон), вместо обычного системного уведомления.
Если пуш не доставлен за эти секунды — звонок почти наверняка уже неактуален,
доставлять его позже нет смысла.

### STUN/TURN

STUN (по умолчанию бесплатный сервер Google) хватает, когда оба участника за
"обычным" NAT — тогда WebRTC договаривается напрямую. Для надёжной связи в
реальных мобильных/домашних сетях (симметричный NAT, мобильные операторы)
без TURN часть звонков просто не соединится. Для продакшена рекомендуется
поднять свой TURN-сервер (например, [coturn](https://github.com/coturn/coturn))
и указать его через `TURN_SERVER_URL` / `TURN_SERVER_USERNAME` / `TURN_SERVER_CREDENTIAL`.
